LensCharacter Engine

A GPU lens simulator for finishing. It reads measured lens profiles and recreates their distortion, chromatic aberration, field aberrations, bokeh and bloom on every frame. Each trait can be isolated, taken from a different lens, and pushed past what the real lens does.

Scope and principles

This engine simulates lenses with code; it is not a colour lookup. A LUT maps one input colour to one output colour and cannot move or spread light across the frame. Our current DCTL can move light, but it runs one pass with no external data, no depth input and no stored state. Lens character needs all of these. Distortion and lateral CA are geometric warps. Coma, fringing and bokeh are point spread functions (PSFs) that change across the frame. Bloom is a long-range redistribution of energy. All of them are driven by measured data and not by hand-tuned constants.

Design principles

  • Physical first, stylised second. Every trait has a measured physical baseline. Stylisation is a controlled deviation from that baseline (see Overdrive), never a separate effect bolted on.
  • Light is linear. All optics run on scene-linear float data. Bright sources keep values above 1.0, so a streetlight becomes a bright bokeh disc without any artificial highlight boost.
  • Everything is a function of field position. Each trait is defined over field height ρ, azimuth φ, f-number N and focus distance df.
  • Traits are independent layers. The data model stores each trait separately, so it can be isolated, mixed or switched off.
  • The ideal lens is always valid. With every trait at zero, the engine skips all passes and returns the input bit-exact.

System overview

The system has an offline half, which turns captures into profiles, and a runtime half inside the host, which turns profiles into pixels. They share one versioned file format.

The CPU side is cheap and runs once per frame: it interpolates the profile, mixes traits, applies overdrive and checks dirty flags. The GPU side does the heavy work. Expensive derived resources, such as warp maps and PSF kernel atlases, are rebuilt only when the inputs that affect them change, never on every frame.

Profile data model

Coordinates

Profiles are stored in sensor units, not pixels, so one profile works at any resolution or crop. Field height is normalised to the lens's image circle:

xmm = (px − cx) · (Wsensor / Wpx) · ssqueeze // pixel → sensor mm, anamorphic de-squeeze
ρ = ‖(xmm, ymm)‖ / Rimage circle, φ = atan2(ymm, xmm) // ρ = 1 at the edge of coverage

The user supplies sensor width and the active crop, or the engine reads them from clip metadata. The optical centre c is a profile value and can be overridden by the user.

Ingestion and per-frame state

On load (once per profile)

  1. Parse the manifest and reject unknown schema versions or unit mismatches.
  2. Resample every ρ-curve onto a canonical grid of 128 samples, ρ ∈ [0, 1.25], to cover overscan.
  3. Upload curves into one 2D float texture (one row per curve) and the SDFs into a texture array.
  4. Cache by content hash in a process-wide store, so ten instances of the same lens share one upload.

Every frame (CPU, microseconds)

state = LensState()
for trait in TRAITS:
    sources = mixer.slots[trait]                       # profile refs + weights
    params  = [interp(p.trait, N, focus, zoom) for p in sources]
    blended = trait.blend(params, weights)            # parameter-space blend (§08)
    state[trait] = overdrive(trait, blended, amount)  # soft-limited (§09)

if hash(state.geometry) != cache.geometry_hash:  bake_stmaps(state)       # §06
if hash(state.psf)      != cache.psf_hash:       bake_psf_atlas(state)    # §07
if hash(state.bloom)    != cache.bloom_hash:     solve_pyramid_weights(state)
upload(state.constants)                           # ~2 KB constant buffer

Aperture and focus distance come from keyframed parameters. When the clip carries Cooke /i or ZEISS XD metadata, they can come from that instead, so a rack focus in the original shot drives the simulated lens.

GPU render graph

Eight stages run in a fixed order. The order follows how a real camera forms an image: geometry first, then the spread of each point of light in the final image plane, then scatter, then shading. Any stage whose trait is zero is skipped.

  1. Input and linearise

    in: source clip · out: RGBA float, scene-linear

    Convert from the timeline working space to scene-linear using the OpenFX 1.5 colour-management API, which Resolve 21 supports. If no colour management is available, use a transfer function the user selects.

  2. Defocus map

    in: depth clip | matte | radial | uniform · out: signed CoC (px), tile min/max

    Thin-lens circle of confusion, signed so the engine knows near from far: c = f²/(N(df−f)) · (d−df)/d. A 16×16 tile pass stores min and max CoC for each tile. Later stages use it to dilate blur across depth edges and to skip work quickly in tiles that are in focus.

  3. Geometric warp (distortion and lateral CA)

    in: linear RGB, CoC · out: warped RGB, warped CoC

    One resample using three baked per-channel STMaps. Filter: Catmull-Rom or Lanczos-3, with an anti-ringing clamp. Overscan policy: fit to frame, extend edges, or leave transparent alpha.

  4. Field-variant PSF and bokeh

    in: warped RGB, CoC, PSF atlas, aperture SDFs · out: defocused RGB

    The heavy pass. Each pixel uses its own kernel, built from field position, CoC per channel, iris shape, cat-eye clipping and coma. Details in §07.

  5. Edge fringing

    in: S3 output, luminance gradient · out: fringed RGB

    Most fringing already comes from the per-channel CoC in S3. This stage adds sensor-side purple fringing next to clipped highlights, at a strength set by the profile.

  6. Bloom, veil and halation

    in: RGB · out: RGB with scattered energy

    A 6–8 level dual-filter pyramid whose level weights are solved to match the measured PSF tail. Energy-conserving: out = (1−e)·I + e·Σ wl·Ll.

  7. Relative illumination and tint

    in: RGB · out: RGB

    Multiply by V(ρc) per channel, then apply the coating matrix. Done in linear light, where gain is physically correct.

  8. Output

    in: RGB · out: working space RGBA

    Scrub NaN and Inf, pass alpha through (or warp it with the image when overscan is transparent), and convert back to the working space.

GPU implementation

Host integration

An OpenFX plugin using the host's GPU render suites. Resolve hands the plugin Metal, CUDA or OpenCL buffers directly, so frames never travel back to the CPU. Intermediate buffers come from the host's memory suite.

One kernel source

Kernels are written once in Slang, or in a C subset with macros like DCTL's, then compiled to MSL, CUDA and OpenCL. A CPU fallback with the same code exists for render farms and tests.

Adaptive cost

Samples per pixel scale with CoC², up to a cap. Tiles with large CoC render at half resolution and are upsampled with a filter that respects CoC edges. Tiles that are in focus use the small PSF atlas only.

Frame budget

Target: under 40 ms per UHD frame on Apple M-series Max and RTX 4080 class GPUs at moderate defocus, so review plays back in real time. These are targets, not measurements.

Distortion and chromatic aberration math

Forward model

The profile describes how the lens moves an ideal (pinhole) image point u to where it lands on the sensor, d:

r² = ux² + uy²
d = u · (1 + k1r² + k2r⁴ + k3r⁶) + [2p1uxuy + p2(r²+2ux²), p1(r²+2uy²) + 2p2uxuy]
// k₁ < 0 → barrel, k₁ > 0 → pincushion, mixed signs on k₁/k₂ → moustache

Inverse mapping for rendering

To render, each output pixel needs the opposite direction: which source point lands here? The engine solves u = D⁻¹(d) with 3–5 Newton iterations per texel, once per parameter change, and bakes the result into an STMap at ¼ resolution (bilinear lookup is accurate enough because the map is smooth). A residual STMap from the profile, if present, is added afterwards.

Lateral CA folded into the same warp

Lateral CA is a slightly different magnification per wavelength. Red/cyan fringes come from mR ≠ 1 and blue/yellow fringes from mB ≠ 1. The sign decides which colour sits on the outer edge:

uc(d) = D⁻¹( d / mc(ρ) ), c ∈ {R, G, B}, mG ≡ 1
// m_R(ρ) > 1 → red pushed outward, cyan edge inward
// m_B(ρ) < 1 → blue pulled inward, yellow edge outward

Because mc is a full curve, not one coefficient, the effect can change sign across the field the way real lenses do. The three channel maps are baked together and S2 samples each channel once. Distortion and CA together cost one pass.

Coma, fringing and bokeh

These three traits are one physical object: the point spread function, at a given field position, focus offset and wavelength. Modelling them together keeps them consistent with each other. A swirly lens's cat-eye bokeh and the coma in its sharp corners come from the same pupil.

From profile to kernel

Pc(x,y; ρ) = A(x,y) · T(r) · Clipcat-eye(x,y; ρ) · exp( i·2π/λc · W(x,y; ρ, Δzc) )
PSFc(ρ) = | 𝓕{ Pc } |² // sharp regime, baked into the atlas
W = Σ Wn,m(ρ)·Znm // Z₂⁰ defocus · Z₂^±2 astigmatism · Z₃^±1 coma · Z₄⁰ spherical
  • Small CoC (in focus or nearly). Diffraction and aberrations dominate. The engine bakes PSFc by FFT at 16 field rings × 3 channels into a 64² kernel atlas. S3 rotates each kernel to the pixel's azimuth φ and convolves directly. This is where coma appears: comet-shaped flare on bright points in the corners, pointing away from the centre.
  • Large CoC (defocused). Geometric optics dominates. The kernel is the pupil projected and scaled by CoC: iris SDF × transmission T(r) × cat-eye clip. S3 evaluates it on the fly with stratified samples in the pixel's tangential frame, so cat-eye and swirl follow the field.
  • Between the two, the engine crossfades over a CoC range set in the profile (about 2–6 px).

Fringing at high-contrast edges

Longitudinal CA gives each channel its own CoC: cc = c + Δzc. In front of the focal plane, red blurs more than blue, and behind it the reverse. That produces the purple-before, green-behind fringes on contrasty edges and the coloured rims on bokeh, with no separate fringe effect. S4 adds only the part that comes from the sensor: purple blooming beside clipped highlights.

Bokeh texture and depth falloff

  • Aperture shape. The SDF for the current stop. Blade count, curvature and rotation are measured, so a 7-blade Super Speed at T2.8 gives heptagons and a round iris wide open gives circles.
  • Texture. T(r) gives bright rims (soap-bubble lenses) or soft edges (apodisation filters). The residual texture adds onion rings from aspherical elements and dust specks.
  • Depth falloff. CoC from S1 grows with distance from the focal plane following the thin-lens curve, so near and far blur fall off at the correct asymmetric rates. Near and far samples are gathered as separate layers, using the tile-dilated CoC, so foreground blur spreads over in-focus edges and not under them.

Trait mixer

The mixer treats a lens as a stack of independent trait slots. Each slot names its source lens and how strongly it applies. The rule that makes mixing work: blend parameters, never pixels. Rendering two lenses and cross-fading the frames gives double images. Blending their descriptions gives one coherent, plausible lens.

Slot structure

{
  "recipe": "Cooke geometry, Blackwing glow",
  "base": "modern-clean-50",                       // fills any slot not listed
  "slots": {
    "distortion": { "sources": [["cooke-s4-32", 1.0]], "overdrive": 1.0 },
    "lateral_ca": { "sources": [["cooke-s4-32", 1.0]], "overdrive": 1.0 },
    "bloom":      { "sources": [["blackwing7-47", 0.8]], "overdrive": 1.4 },
    "bokeh":      { "sources": [["helios-44-2", 0.6], ["blackwing7-47", 0.4]] },
    "field_psf":  { "link": "bokeh" }              // keeps coma consistent with the pupil
  },
  "field_basis": "normalized_height"               // or "field_angle"
}

A weight below 1 blends toward the ideal lens (zero deviation). Several sources in one slot are combined with normalised weights. Recipes refer to profiles by ID and content hash, so a recipe still reproduces exactly after the profile library is updated.

Mixing lenses of different formats

Traits taken from a 32 mm lens and applied to a plate shot on a 75 mm need a shared reference. With normalised image height (the default), the trait covers the frame the same way it covered the original image circle. With field angle, it maps by real viewing angle, which is better for matching a wide lens's corner behaviour on a tighter shot.

Linked traits

Some traits share a physical cause. By default they are linked so they move together, and the user can unlink them on purpose:

  • Cat-eye, swirl, field curvature and coma all come from pupil geometry and off-axis aberrations.
  • Longitudinal CA drives both bokeh rims and edge fringing.
  • Relative illumination and cat-eye clipping both come from mechanical vignetting.

Overdrive

Every trait parameter is stored as a deviation from the ideal lens, θ = θ0 + Δ. Overdrive amount o scales the deviation. Up to o = 1 it is exact physical scaling. Above 1 it extrapolates into stylised territory, passing through a soft limiter tuned to that trait's validity budget B. The budget is the point where the image would break: a warp folding over itself, a kernel larger than the sampler covers, or energy that no longer adds up.

Δ′ = sign(Δ) · B · S( o·|Δ| / B ), S(x) = x / (1 + x⁴)^¼
// S(x) ≈ x for x ≪ 1: subtle traits scale linearly, so o = 2 really doubles them
// S(x) → 1 as x → ∞: any amount of overdrive stays inside the budget

Budgets per trait

TraitBudget B: what it protects
DistortionThe warp stays one-to-one: ∂(r·f(r))/∂r > ε across ρ ∈ [0, 1.25]. Solved numerically per recipe at bake time, so barrel never folds into a mirrored ring.
Lateral CAChannel separation up to 2% of the diagonal. Past that, channels become separate ghost images (available in Unbounded mode).
Bokeh and PSFKernel radius stays within the sampler's coverage (10% of frame height). Kernels always sum to 1, so overdrive changes shape, never exposure.
ComaKernel centroid shift stays under the kernel radius, so flare trails but never detaches from its source.
BloomEnergy fraction e ≤ 0.95, so detail is never fully replaced by glow.
VignettingGain floor of −6 stops, so corners never reach zero or produce NaNs in later log-space grading.

Further stylisation controls

  • Field shaping. Remap where a trait appears with ρ′ = ργ. When γ < 1, edge character such as swirl and cat-eye moves toward the centre of frame.
  • Negative overdrive. Inverts the deviation: barrel becomes pincushion, and red-outside CA becomes blue-outside.
  • Anisotropic overdrive. Scales only the tangential or radial part of a kernel, for example extreme swirl without extra radial smear.
  • Unbounded mode. Turns the soft limiter off for deliberate breakage, behind a warning in the UI.
Data guarantees at any settingFloat32 throughout, highlights never clamped, kernels normalised, NaN and Inf scrubbed, alpha preserved, output deterministic per frame (no unseeded noise), and the identity lens returns the input bit-exact.

Validation

  • Round trip. Render synthetic charts (dot grid, slanted edges, point grid, flat field) through the engine with a profile. Run the profile compiler's own analysis on the renders and compare with the real captures: distortion RMS in pixels, MTF50 by field position, CA separation, vignetting curve.
  • Golden images. Each backend (Metal, CUDA, OpenCL, CPU) must match stored reference frames within a fixed tolerance on every build.
  • Invariants. Identity recipe is bit-exact. Kernel energy sums to 1. Warps stay one-to-one up to the budget. No NaN for any input, including Inf and negative values.
  • Side-by-side review. Shoot the same scene on the real lens and on a clean reference lens, then process the reference with the engine and compare. This is the final check that matters for a colourist.

Roadmap from the DCTL prototype

The current LensCharacter.dctl already contains the kernel logic for the iris polygon, cat-eye clipping, tangential swirl, per-channel rims and Vogel sampling. That code moves into S3 nearly unchanged. Its hard-coded preset table becomes the first set of hand-made profiles until measured ones exist.
